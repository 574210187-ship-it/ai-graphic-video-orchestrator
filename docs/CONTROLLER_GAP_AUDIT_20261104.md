# 控制器接入缺口审计｜2026-11-04

## 已有能力

- `gvflow` 已覆盖候选筛选、来源下载、状态机、阶段0、计划、产物校验、飞书上传/字段回写和同行回读。
- 候选并集规则已固定：优先 `二次分类型=图文`，其次 `类型=图文` 且二次分类型为空或其他值。
- ChatGPT Work 和 DeepSeek Harness 已有准备指令和全流程指令。
- 普通双分支、律师单分支、单行失败继续、部分写回恢复已有离线测试。

## 原有缺口

1. 没有 Muse、Grok Bot、ChatGPT Dot 的独立接入指令；三者容易各自解释流程。
2. 控制器合同没有统一要求 `controller_id`、`actor_id`、能力探测和持久检查点。
3. 只用本地文件锁时，跨电脑仍可能出现两个 Bot 同时写同一个 Base；没有共享租约时不能并发。
4. 旧交接文字虽然写了“单行失败继续”，但没有强制 Bot 进入持久循环，容易完成一行后等待用户。
5. 旧文档没有把“网页回复不等于 MP4、PID不等于运行、结果必须由 gvflow写回”作为三条不可绕过的硬门。
6. 公开记忆是脱敏摘要，不是逐字聊天记录；原始聊天、凭据和私有运行数据不应进入公开仓库。

## 本次补齐

- 新增 `UNIVERSAL_BOT_CONTROLLER_CONTRACT.md`，把五类控制器统一到同一输入、输出、能力、互斥、恢复和最终清零合同。
- 新增 Muse、Grok Bot、ChatGPT Dot 三份全流程复制指令。
- 明确三者可分别运行，但没有共享租约时只能一次启用一个生产写入者。
- 明确 Bot 缺少命令、文件、浏览器或飞书写能力时必须使用 Bridge，不能假装已接通。
- 明确单行失败只进恢复队列并继续；只有全局故障才暂停整批。
- 明确公开仓库只保留脱敏长期记忆；私有仓库保存更完整的窗口快照，不能把原始全聊天和敏感数据公开。

## 仍需在各 Bot 本机实测的内容

- Muse 是否能在自己的云电脑持久运行 `gvflow` 并真正拿到 MP4；
- Grok Bot 是否有可持续的浏览器和本地文件桥；
- ChatGPT Dot 是否有命令执行、下载和飞书写回通道；
- 三者各自的专用空成品写权限测试；
- 如果要并发，新增并实测共享租约服务或飞书租约表。

这些不是文档可以凭空证明的能力，必须由对应 Bot 生成 `capability_probe.json`、测试记录和真实飞书回读证据。
